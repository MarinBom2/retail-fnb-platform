# 제품 전략 — 다점포 리테일·외식 체인을 위한 B2B 매장 운영 플랫폼

> 목적: 이 소프트웨어를 **누구에게, 무엇을 약속하고, 어떻게 파는지**를 정하고, 그 약속이 코드의 어느 기능에 기대는지 잇는다.
> 숫자 규칙: 시장 규모·전환율·고객 수 같은 숫자는 지어내지 않는다. 측정하거나 출처를 확인한 뒤 채운다 (`[ ]`).
> 관련 문서: [domain-design.md](./domain-design.md), [api.md](./api.md)

## 1. 풀려는 문제

| 업종 | 매장에서 실제로 생기는 일 | 지금 흔한 처리 방식 |
|---|---|---|
| 생활용품 | SKU 가 많아 품절을 늦게 안다. 손님이 찾는 상품이 옆 매장에는 남아 있다 | 매장끼리 전화·메신저로 재고를 묻고, 수기로 옮긴 뒤 각자 재고를 고친다 |
| 의류 | 같은 스타일에서 특정 사이즈만 빠진다. 사이즈가 없으면 손님이 그냥 나간다 | 직원이 다른 매장에 전화해 "BLACK L 있어요?"를 묻는다 |
| 외식 | 메뉴는 팔리는데 식자재가 언제 떨어질지 모른다. 바쁜 시간에 재료가 바닥난다 | 마감 후 눈대중 재고, 다른 지점에 급히 빌린다 |

공통점: **재고 정보가 매장 안에 갇혀 있고, 매장 사이의 이동이 시스템 밖(전화·메신저)에서 일어난다.** 그래서 이동한 재고가 장부에 늦게 반영되고, 본사는 어느 매장이 무엇을 들고 있는지 모른다.

## 2. 가치 제안과 그것을 받치는 기능

| 약속 | 화면 | 받치는 코드 |
|---|---|---|
| 품절이어도 판매를 놓치지 않는다: POS 에서 재고가 없으면 같은 브랜드 다른 매장 재고를 바로 보고 한 번에 이동을 요청한다 | SCR-05 POS, SCR-07 재고 | `StockAvailabilityFinder`, `OUT_OF_STOCK` + `skuId`, `POST /transfers` |
| 매장 간 이동이 장부에서 일어난다: 요청 → 승인 → 출고 → 입고, 단계마다 시각과 담당 매장이 남고 재고가 자동으로 바뀐다 | SCR-08 이동 | `StockTransfer`, `StockTransferService`, 원장 `TRANSFER_OUT/IN` |
| 떨어지기 전에 안다: 안전재고 이하 품목을 대시보드에 띄우고, 재고가 가장 많은 매장을 추천한다 | SCR-04 대시보드 | `Stock.needsReorder`, `DashboardResponse.lowStock.bestSource*` |
| 업종이 달라도 한 시스템: 생활용품은 바코드, 의류는 색상×사이즈, 외식은 테이블·포장 | SCR-05 POS | `BusinessType`, `ProductKind`, `OrderType` 규칙 |
| 외식은 메뉴를 팔면 식자재가 빠진다: 레시피 기반 차감으로 재료 소진을 실시간으로 본다 | SCR-05, SCR-07 | `RecipeStockDeduction` |
| 재고 숫자를 믿을 수 있다: 모든 변동이 원장에 남고 잔량이 함께 기록된다 | SCR-07 이력 | `StockMovement.balanceAfter` |
| 권한이 매장 단위다: 직원은 판매만, 재고를 바꾸는 일은 점주·매니저만 | 전 화면 | `StoreAccessGuard`, `StaffRole.canManageInventory` |

## 3. 경쟁 구도 (조사해서 채운다)

| 구분 | 예 | 잘하는 것 | 우리가 다르게 하는 것 |
|---|---|---|---|
| 단일 매장 POS | `[ ]` | 결제·영수증 | 매장 간 재고·이동이 없다 |
| 업종 전용 ERP | `[ ]` | 본사 회계·발주 | 매장 현장(POS)과 이동이 분리돼 있다 |
| 외식 전용 주문 시스템 | `[ ]` | 테이블 주문 | 리테일 재고 모델이 없다 |

`[ ]` 에는 실제로 확인한 제품만 적는다. 기능 비교는 공개 자료로 확인한 범위까지만 쓴다.

## 4. 가격 (가설)

| 플랜 | 대상 | 포함 | 과금 단위 |
|---|---|---|---|
| Store | 매장 1~2곳 | POS, 매장 재고, 대시보드 | 매장당 월 `[ ]`원 |
| Chain | 매장 3곳 이상 | + 매장 간 이동, 다른 매장 재고 찾기, 안전재고 추천 | 매장당 월 `[ ]`원 |
| Enterprise | 본사 연동 | + 본사 대시보드, 외부 ERP·회계 연동, 전용 지원 | 계약 |

- **Chain 이 핵심 플랜이다.** 매장 간 이동은 매장이 여러 곳일 때만 값이 생긴다. 가격 실험은 데모 뒤 파일럿 고객 인터뷰로 정한다 `[ ]`.
- 결제(PG·카드 단말)는 직접 하지 않고 연동한다. 주문에는 결과(수단·시각)만 남긴다.

## 5. 영업과 도입

1. **데모** (30분): `demo` 프로필 서버로 세 업종을 돌며 아래 시나리오를 보여 준다.
2. **파일럿** (매장 3곳, `[ ]`주): 한 브랜드의 직영점 3곳. 상품 마스터를 넣고 POS 와 재고만 먼저 쓴다.
3. **확장**: 이동·안전재고를 켜고 나머지 매장을 붙인다.

**데모 시나리오 (계정 `demo@retailfnb.dev` / `Demo1234!`)**

| 순서 | 매장 | 보여 줄 것 |
|---|---|---|

| 2 | 강남점 POS | 우산(품절)을 담고 결제 → 재고 부족 → 다른 매장 재고 → 이동 요청 |

## 6. 도입 성과를 재는 법 (파일럿에서 측정)

| 지표 | 정의 | 측정 |
|---|---|---|
| 이동으로 살린 판매 | POS 품절에서 시작한 이동 요청 중 입고 후 판매된 수량 | 이동·주문 원장 대조 `[ ]` |
| 이동 리드타임 | 요청 → 입고 시간 (중앙값) | `requestedAt`, `receivedAt` |
| 품절 시간 | SKU 가 0 이었던 시간 합 | 원장 `balanceAfter` |
| 재고 정확도 | 실사 차이 / 장부 수량 | `ADJUST` 원장의 `delta` |
| 매장 활성도 | 주간 POS 결제가 있는 매장 비율 | 주문 |

## 8. 지키는 것

- 시연·자료에 **실제 회사 상호·로고를 쓰지 않는다**. 데모 브랜드는 가상 이름이다 (데일리마트, 핏앤코, 온기식당).
- 숫자는 측정한 값만 쓴다. 고객 사례·추천사는 실제 고객 동의를 받은 것만 쓴다.
- 결제 카드 정보는 다루지 않는다 (PG 가 맡는다).
